# DevOps & QA Architecture — TripVlog AI Generator

> **Conclusion**: The infrastructure runs on GCP Cloud Run with three service types (API Service, Worker Service, FFmpeg Jobs), uses a 5-stage FFmpeg pipeline with per-stage GCS checkpointing, deploys via GitHub Actions with canary traffic splitting, and enforces 80%+ test coverage through a mandatory CI gate. All secrets are managed via GCP Secret Manager with zero hardcoded credentials.

## 1. GCP Cloud Run Architecture

### Service Breakdown

| Service | Type | Purpose | Scaling | Resources |
|---------|------|---------|---------|-----------|
| `tripvlog-api` | Cloud Run Service | REST API, user auth, project management | 1-10 instances, concurrency 80 | 2 vCPU, 4 GiB |
| `tripvlog-worker` | Cloud Run Service | Async job orchestration, Gemini/Veo3 API calls | 1-5 instances, concurrency 10 | 2 vCPU, 8 GiB |
| `tripvlog-ffmpeg` | Cloud Run Job | FFmpeg video processing (batch) | Task-based, 0 idle | 8 vCPU, 32 GiB |

### Why Cloud Run Jobs for FFmpeg

Cloud Run Services impose a 300-second request timeout. FFmpeg processing for a 10-minute vlog takes 10-20 minutes. Cloud Run Jobs support:
- Up to 3600s (1 hour) task timeout
- Up to 8 vCPU + 32 GiB memory per task
- No HTTP listener required — pure batch execution
- Built-in retry with configurable `maxRetries`
- Task parallelism for multi-clip transcoding

## 2. FFmpeg Pipeline

### Pipeline Architecture

The FFmpeg pipeline has 5 stages. Each stage is an atomic unit that reads from GCS, processes, and writes back to GCS. This enables:
- **Retry at any stage** without re-processing earlier stages
- **Debugging** by inspecting intermediate outputs in GCS
- **Parallelism** in Stage 1 (transcode multiple clips concurrently)

```
Stage 1: Transcode    Stage 2: Cross-dissolve    Stage 3: Captions
┌─────────────┐       ┌──────────────────┐       ┌──────────────┐
│ Raw clips    │──────▶│ Normalized clips │──────▶│ Stitched     │───▶
│ (mixed fmt)  │       │ → xfade filter   │       │ + subtitles  │
└─────────────┘       └──────────────────┘       └──────────────┘

Stage 4: BGM Mix       Stage 5: Final Export
┌──────────────┐       ┌──────────────────┐
│ Captioned    │──────▶│ Mixed video      │──────▶  Final MP4
│ + BGM audio  │       │ → H.264 export   │
└──────────────┘       └──────────────────┘
```

### Stage Details

#### Stage 1: Transcode to Normalized Format

**Purpose**: Normalize all input media to a consistent format for reliable downstream processing.

```bash
ffmpeg -i "$INPUT" \
  -vf "scale=1920:1080:force_original_aspect_ratio=decrease,pad=1920:1080:(ow-iw)/2:(oh-ih)/2" \
  -r 24 \
  -c:v libx264 -preset medium -crf 18 \
  -c:a aac -ar 48000 -ac 2 \
  -f mp4 "$OUTPUT"
```

- `force_original_aspect_ratio=decrease,pad` handles mixed aspect ratios (landscape/portrait) by letterboxing
- CRF 18 for high quality intermediate (not final bitrate-constrained yet)
- Parallelizable: each clip transcodes independently → multiple Cloud Run Job tasks

#### Stage 2: Cross-Dissolve Stitching

**Purpose**: Join scenes with smooth transitions based on storyboard JSON from Gemini.

```bash
# Offsets calculated by Python script (NEVER mental math)
python3 scripts/calculate_xfade_offsets.py --storyboard storyboard.json --output offsets.json

# Generated FFmpeg command for 3 clips:
ffmpeg \
  -i clip1.mp4 -i clip2.mp4 -i clip3.mp4 \
  -filter_complex "
    [0:v][1:v]xfade=transition=fade:duration=1:offset=4.0[v01];
    [v01][2:v]xfade=transition=fade:duration=1:offset=6.0[vout];
    [0:a][1:a]acrossfade=d=1[a01];
    [a01][2:a]acrossfade=d=1[aout]
  " \
  -map "[vout]" -map "[aout]" \
  -c:v libx264 -crf 18 output_stitched.mp4
```

#### Stage 3: Caption Overlay

**Purpose**: Burn in or soft-overlay captions from SRT file.

```bash
# Soft subtitles (user can toggle in player)
ffmpeg -i input.mp4 -i captions.srt \
  -c copy -c:s mov_text \
  -metadata:s:s:0 language=eng \
  output_captioned.mp4

# Burned-in subtitles (always visible)
ffmpeg -i input.mp4 \
  -vf "subtitles=captions.srt:force_style='FontSize=24,PrimaryColour=&H00FFFFFF,OutlineColour=&H00000000,Outline=2'" \
  -c:v libx264 -crf 18 -c:a copy \
  output_captioned.mp4
```

#### Stage 4: BGM Audio Mix

**Purpose**: Mix background music with original audio, applying loudness normalization.

```bash
ffmpeg -i video.mp4 -i bgm.mp3 \
  -filter_complex "
    [0:a]loudnorm=I=-16:TP=-1.5:LRA=11[speech];
    [1:a]volume=0.15,afade=t=in:d=2,afade=t=out:st=DURATION_MINUS_3:d=3[music];
    [speech][music]amix=inputs=2:duration=first:dropout_transition=3[aout]
  " \
  -map 0:v -map "[aout]" \
  -c:v copy -c:a aac -b:a 192k \
  output_mixed.mp4
```

- `loudnorm` EBU R128 normalization ensures consistent speech volume
- BGM at 15% volume with 2s fade-in and 3s fade-out
- `duration=first` truncates BGM to match video length
- BGM duration math calculated via Python script

#### Stage 5: Final Export

**Purpose**: Encode to delivery-ready format with target bitrate.

```bash
ffmpeg -i input.mp4 \
  -c:v libx264 -preset slow -b:v 8M -maxrate 10M -bufsize 16M \
  -profile:v high -level 4.1 \
  -c:a aac -b:a 192k -ar 48000 \
  -movflags +faststart \
  -f mp4 final_output.mp4
```

### Error Handling

| Failure Mode | Detection | Recovery |
|-------------|-----------|----------|
| FFmpeg segfault / OOM | Non-zero exit code + Cloud Run Job task failure | Retry task (max 2 retries), if persistent → increase memory allocation |
| Corrupt input file | FFmpeg stderr: "Invalid data" | Skip file, log warning, continue with remaining clips |
| GCS download timeout | Python GCS client timeout exception | Retry with exponential backoff (1s, 2s, 4s) |
| Disk space exhaustion | `No space left on device` | Each stage downloads from GCS → processes locally → uploads to GCS → deletes local files. Only one stage's working files exist on disk at a time. If a single stage's files exceed available memory, split into sub-batches (e.g., transcode 5 clips at a time in Stage 1). |
| Stage timeout (>30 min) | Cloud Run Job task timeout | Alert, investigate input size, consider splitting into smaller jobs |

### Storage I/O Pattern Per Stage

> **Critical**: Cloud Run's `/tmp` is backed by RAM (tmpfs), sharing the 32 GiB memory limit with the FFmpeg process. Intermediates must NOT accumulate on tmpfs across stages.

Each stage follows this strict I/O pattern:

```
1. Download inputs from GCS to /tmp/stage-N-in/
2. Run FFmpeg (reads /tmp/stage-N-in/, writes /tmp/stage-N-out/)
3. Upload /tmp/stage-N-out/ to GCS bucket (tripvlog-intermediate-renders/{job_id}/stage-N/)
4. Delete /tmp/stage-N-in/ and /tmp/stage-N-out/
5. Next stage starts fresh — downloads only its own inputs from GCS
```

**Memory budget (32 GiB total):**
- FFmpeg process: ~4-8 GiB (depends on filter complexity)
- tmpfs input files: max ~10 GiB (one stage's inputs)
- tmpfs output files: max ~10 GiB (one stage's outputs)
- Safety margin: ~4 GiB

**Stage 1 sub-batching**: When transcoding 20+ clips, process in batches of 5 clips to keep tmpfs usage under 10 GiB. Each batch: download 5 → transcode → upload to GCS → delete local → next batch.

### Deployment Strategy: Canary with Alert-Driven Rollback

> **Note**: Rollback is **semi-automated** — a Cloud Monitoring alert triggers a Cloud Function that executes the rollback. No human watches a dashboard. However, the Cloud Function must be deployed and the alert policy configured correctly for this to work. If the alert policy or Cloud Function is misconfigured, rollback requires manual intervention.

**Steps:**

1. **Deploy new revision** with `--no-traffic` tag
2. **Route 10% traffic** to canary revision
3. **Run smoke tests** against canary URL (CI pipeline, not manual)
4. **Cloud Monitoring alert** watches 5xx error rate on canary tag for 5 minutes
5. **If alert fires** → Cloud Function `rollback-canary` executes `gcloud run services update-traffic --to-revisions PREVIOUS=100`
6. **If no alert after 5 min** → CI pipeline promotes to 100%

```bash
# Canary deployment
gcloud run deploy tripvlog-api \
  --image $IMAGE \
  --region us-central1 \
  --tag canary \
  --no-traffic

# Route 10% to canary
gcloud run services update-traffic tripvlog-api \
  --region us-central1 \
  --to-tags canary=10

# After smoke tests pass AND no alert fired → promote
gcloud run services update-traffic tripvlog-api \
  --region us-central1 \
  --to-latest
```

**Rollback Cloud Function (triggered by alert policy):**

```python
# cloud_functions/rollback_canary/main.py
import functions_framework
from google.cloud import run_v2

@functions_framework.http
def rollback_canary(request):
    """Triggered by Cloud Monitoring alert when canary error rate > 5%."""
    client = run_v2.ServicesClient()
    service_name = "projects/PROJECT_ID/locations/us-central1/services/tripvlog-api"

    # Get current traffic config, remove canary tag, restore 100% to previous
    service = client.get_service(name=service_name)
    service.traffic = [run_v2.TrafficTarget(
        type_=run_v2.TrafficTargetAllocationType.TRAFFIC_TARGET_ALLOCATION_TYPE_LATEST,
        percent=100,
    )]
    client.update_service(service=service)
    return "Canary rolled back", 200
```

**Alert policy that triggers the rollback:**

```yaml
# Cloud Monitoring alert policy
displayName: "Canary Error Rate > 5%"
conditions:
  - displayName: "5xx rate on canary"
    conditionThreshold:
      filter: >
        resource.type="cloud_run_revision"
        AND resource.labels.service_name="tripvlog-api"
        AND resource.labels.revision_name=monitoring.regex.full_match(".*canary.*")
        AND metric.type="run.googleapis.com/request_count"
        AND metric.labels.response_code_class="5xx"
      aggregations:
        - alignmentPeriod: 60s
          perSeriesAligner: ALIGN_RATE
      comparison: COMPARISON_GT
      thresholdValue: 0.05
      duration: 300s   # sustained over 5 minutes
notificationChannels:
  - projects/PROJECT_ID/notificationChannels/CLOUD_FUNCTION_CHANNEL
  - projects/PROJECT_ID/notificationChannels/SLACK_OPS_CHANNEL
```

### Authentication: Workload Identity Federation

CI/CD authenticates to GCP using **Workload Identity Federation** (WIF) — no service account key files:

```yaml
- uses: google-github-actions/auth@v2
  with:
    workload_identity_provider: projects/PROJECT_NUM/locations/global/workloadIdentityPools/github/providers/github
    service_account: ci-deploy@PROJECT_ID.iam.gserviceaccount.com
```

This is more secure than storing JSON key files in GitHub secrets because:
- No long-lived credentials to rotate
- Federated identity tokens are short-lived (1 hour)
- Scoped to specific GitHub repos/branches

## 5. Secret Management

### Zero-Secret-Leak Architecture

```
┌──────────────────────────────────────────────────────┐
│                  Secret Flow                          │
│                                                      │
│  Developer's .env ──(gitignored)──▶ Local dev only   │
│                                                      │
│  GCP Secret Manager ──▶ Cloud Run env vars           │
│       │                  (injected at deploy time)   │
│       │                                              │
│  GitHub Actions Secrets ──▶ CI env vars              │
│       │                     (WIF token, not keys)    │
```

### Log Sanitizer

All application logs must pass through a sanitizer before emission to Cloud Logging:

```typescript
// src/lib/log-sanitizer.ts
const SECRET_PATTERNS = [
  /AIza[0-9A-Za-z\-_]{35}/g,                    // Google API key
  /ya29\.[0-9A-Za-z\-_]+/g,                     // Google OAuth token
  /sk-[a-zA-Z0-9]{48,}/g,                       // Generic API key
  /eyJ[A-Za-z0-9\-_]+\.eyJ[A-Za-z0-9\-_]+/g,   // JWT token
];

function sanitize(message: string): string {
  return SECRET_PATTERNS.reduce(
    (msg, pattern) => msg.replace(pattern, '[REDACTED]'),
    message
  );
}
```

### Alert Policies

| Alert | Condition | Severity | Notification |
|-------|-----------|----------|--------------|
| High Error Rate | 5xx rate > 5% over 5 min | CRITICAL | PagerDuty + Slack |
| Job Failure Spike | FFmpeg job failure > 3 in 15 min | HIGH | Slack #ops |
| Queue Backlog | Pub/Sub backlog > 50 messages for 10 min | HIGH | Slack #ops |
| CPU Saturation | Cloud Run CPU > 80% for 10 min | MEDIUM | Slack #ops |
| Storage Cost Spike | Daily GCS cost > $50 (2x normal) | MEDIUM | Email + Slack |
| API Latency | p99 latency > 5s for 5 min | HIGH | Slack #ops |
| Memory Pressure | Cloud Run memory > 90% | HIGH | PagerDuty |
| Secret Access Anomaly | Secret Manager access from unexpected SA | CRITICAL | PagerDuty + Email |
